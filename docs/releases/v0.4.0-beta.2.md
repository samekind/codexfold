# CodexFold v0.4.0-beta.2

This prerelease makes the fold hand the space back. The previous preview could
fold a real corpus and keep folding it, but the reclamation that deletes what
the fold replaced could never run while the service was up: the daemon held a
writer lease on every managed session, and the cleanup needs to lock all of
them. Superseded pack generations therefore accumulated beside the one in use.
On the maintainer's store that was 16.4 GB of retained duplicate libraries
holding the reported saving at 18.8% while folding itself had already reached
three quarters of the corpus.

It also makes a fix deliverable. Until now every daemon change meant stopping
the service, which means dropping the mount under a running Codex.

## Highlights

- Reclamation no longer blocks itself. The writer lease is held for recovery
  mutual exclusion rather than for the life of the daemon. On the 2,435-session
  production store this took retained pack generations from four to two, the
  pack directory from 23 GB to 10 GB, and the reported saving from 18.8% to
  **69.1%** (41.69 GB logical in 12.89 GB physical).
- `fs service update-daemon-live` replaces only the daemon. Codex, the
  supervisor and the FSKit mount stay up. The candidate must answer
  `fs serve --help` with the required backend flags before the running daemon is
  signalled, and one that does not take over within nine seconds is rolled back.
- Cold start recovers sessions eight at a time and stops rewriting a writer
  lease and an unchanged mount acknowledgement per session. Backend readiness on
  a 2,435-session fixture went from about 45.9s to about 4.8s.
- Enrollment planning loads the storage inventory once per round while still
  reading live free space per decision: about 6.2s for the first inventory, then
  about 0.3ms for the next 200 decisions. An idle heartbeat stops rescanning
  every managed state every two seconds.
- A cycle catches up manifests an earlier cycle left unpacked, and
  `retire-loose` repacks and retries instead of deleting an original the pack
  does not yet cover.
- An old generation is collectible once its reader leases are released and the
  per-object deletion proof passes. The full pack and manifest readback and the
  per-object proof remain; only a duplicate whole-store doctor pass was removed.
- A service binary whose signing team differs from the launcher's is refused
  before it is installed.

## What Went Wrong Before

- The daemon held a writer lease on all 2,186 managed sessions, measured as
  2,186 held and 0 free. Reclamation runs as child processes, and an flock
  belongs to the open file description, so a child could never take a lock its
  parent held. Every cycle reported `reclaim_deferred=true` with
  `native_proof_passes=0`, and three complete 7.5-7.8 GB pack generations were
  retained beside the one in use.
- Replacing the daemon took the mount down with it, so the only way to ship a
  daemon fix was a maintenance window under a running Codex.
- A cold start recovered 2,186 sessions serially and fsynced a writer lease per
  session, taking about 45.9s to become ready. The live-update takeover deadline
  had only ever been measured against a single-session mount at about 1.5s, so
  the first production attempt at a live replacement failed and rolled back.
- Enrollment planning rescanned the whole store for every candidate it priced,
  holding the daemon above 100% CPU and leaving the cycle stuck in `checking`.
- A managed-state inspection cache compared modification and change timestamps
  to decide a store was unchanged. Linux quantises those to the kernel tick, so
  a same-size rewrite or a directory addition within one tick was
  indistinguishable from no change. This cache sits on the path that proves an
  object is unreferenced before deletion.
- An ad-hoc signed `go build` output installed as the service binary was killed
  by macOS about a second after each launch with an invalid code signature,
  having written nothing to the service log, because the Team-signed launcher
  may not exec it. It passed `codesign --verify` and ran normally from a shell.

## Validation

- The production store reports 2,435 managed sessions healthy through the
  mount, 41.69 GB logical in 12.89 GB physical, with `writer.lease` held on 0 of
  2,435 sessions.
- A real `update-daemon-live --apply` on the production service replaced the
  daemon while the mount was preserved, verified against the running and
  on-disk build SHA, 2,186 managed sessions reporting healthy, three existing
  session digests, and 900/900 consecutive reads.
- Repeated old-to-new takeovers on an isolated native FSKit mount with a
  2,435-session fixture: 3.57s and 3.26s to backend readiness, 4.75s and 3.97s
  total handover, 274 reads / 61 writes and 93 reads / 60 writes with zero
  errors.
- A candidate that exits immediately was injected and rolled back in about
  7.49s with the mount intact and zero probe errors.
- A real 19,596,874-byte archived session folded 0/8 to 8/8 on an isolated
  mount with `fold doctor` and `pack doctor` clean, zero loose objects, and
  physical use down from 19,619,840 to 8,732,672 bytes. An unmodified Codex CLI
  then appended 48,803 bytes to the delta with the recorded prefix unchanged and
  the JSONL still valid.
- A read-only `pack doctor` over the production store read back all 1,305,907
  objects of the current generation.
- `go test -race ./... -count=1` passes on macOS and on Linux (ext4, non-root,
  with `lsof`, matching the CI runner), together with `go vet ./...`, `gofmt`,
  `go mod tidy`, the release metadata check, the public-script sanitisation
  check, and the native FSKit cache test.

## Known Limitations

- The public capability remains `fs-engine-preview`. `production-ready:*` is
  still blocked by the evidence matrix in the maintainer guide, not by elapsed
  time; automatic updates stay refused before that promotion.
- `update-daemon-live` covers the daemon only. App and FSKit extension changes
  still need a maintenance window, and the mount being preserved does not prove
  that every read and write in that window succeeds. Takeover testing has not
  reproduced a production-sized manifest tail or forcibly severed an in-flight
  write.
- Folding needs free space before it can reclaim any: a pack build is refused by
  the free-space reserve on a nearly full volume, and large sessions report
  `insufficient-storage-budget` until earlier ones free room.
- `pack build` rewrites the whole pack each cycle. Batch sizing amortises that
  cost; it does not remove it.
- The real Desktop GUI was not accepted in this round, and a CLI result does not
  substitute for it.

## Install the CLI

```sh
go install github.com/samekind/codexfold/cmd/codexfold@v0.4.0-beta.2
```

The GitHub Release provides checksum-covered default CLI archives for macOS,
Linux, and Windows on `amd64` and `arm64`. These archives expose the local
storage and recovery command surface; they do not contain a generally signed
macOS FSKit App.
