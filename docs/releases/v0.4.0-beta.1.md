# CodexFold v0.4.0-beta.1

This prerelease makes periodic enrollment survive a real corpus. The previous
preview could fold, but a single refusal anywhere in a cycle left the store
unable to make progress again, and nothing recovered on its own. Folding a
2,800-session store surfaced five separate ways to get permanently stuck, each
of which silently blocked every later cycle.

## Highlights

- Batch size is measured rather than assumed. A cycle rebuilds the whole pack
  whether it folds one session or two hundred, so the batch is derived from the
  rebuild and per-session costs recent cycles measured, keeping that fixed toll
  to roughly a quarter of the work. The Auto fold pane gains a "How many per
  pass" control, and `batch_size: 0` in `<store>/enrollment/policy.json` selects
  the automatic setting.
- A staged canonical snapshot that is byte-identical to its source is reused
  instead of refused, so a migration that failed after staging can be retried.
- A failed migration no longer skips reclamation. Only deleting a user's
  original waits for a clean cycle.
- Enrollment planning consults the batch limit before pricing a candidate
  against the storage budget, because each price is a full store scan.
- A cycle repacks once before the storage-health gate blocks it, so a pack build
  refused for free space no longer locks enrollment permanently.
- A mount-table probe that exceeds its deadline is inconclusive rather than an
  outage, gated on the backend still answering.
- A status channel that stops advancing degrades the indicator and escalates
  only once sustained; a component reporting failure still alerts at ten
  seconds.
- Read-ahead extends its horizon only after a read advances into the adjacent
  block.

## What Went Wrong Before

These are the behaviours this release removes, with the numbers the production
store recorded.

- 237 sessions sat folded into the pack with their originals still on disk,
  because a staged snapshot could never be re-staged. That duplication was the
  884 MB behind a reported saving of zero.
- One unroutable session stopped reclamation while the same cycle's pack build
  had already written a new generation, so the store grew every cycle.
- Pricing every candidate against the storage budget took planning from 0.42s
  to over 200s, where it was killed. The Host reported nothing left to fold and
  stopped.
- 12,776 mount probes exceeded their deadline and were reported as recovery,
  each surfacing as a "needs attention" alert that healed itself within half a
  minute. A measured `getfsstat` on the same machine returns in 68 µs at the
  median and 542 µs at p99; the deadline was missed because the probe goroutine
  was not scheduled, not because the filesystem was slow.

## Validation

- 205 sessions whose native originals had been retired were read back through
  the mount and compared against the SHA-256 recorded at retirement: 666 MB,
  byte-identical, every JSONL record still parseable. The originals no longer
  exist, so the recorded digest is the only reference.
- A real `pack build` over the production store compressed 748.50 MiB of raw
  session bytes into 400.35 MiB.
- `fs retire-native --apply` on a live session reclaimed 98% of the original
  file while the mount continued to serve the exact same bytes and size.
- A real `reboot -q` interruption ran at the durable-journal / partial-tail
  checkpoint. On the next boot, automatic recovery restored the exact base
  SHA-256, rejected partial data, cleared the journal, and the independent
  Pack-only FSKit canary returned to 11 healthy doctor components with its
  256 MiB fixture unchanged.

## Known Limitations

- The public capability remains `fs-engine-preview`. Automatic updates are
  still refused before platform production readiness, and promotion is
  explicit.
- Folding needs free space before it can reclaim any: a pack build is refused
  by the free-space reserve on a nearly full volume, and large sessions report
  `insufficient-storage-budget` until earlier ones free room.
- `pack build` rewrites the whole pack each cycle. Batch sizing amortises that
  cost; it does not remove it.

## Install the CLI

```sh
go install github.com/samekind/codexfold/cmd/codexfold@v0.4.0-beta.1
```

The GitHub Release provides checksum-covered default CLI archives for macOS,
Linux, and Windows on `amd64` and `arm64`. These archives expose the local
storage and recovery command surface; they do not contain a generally signed
macOS FSKit App.
